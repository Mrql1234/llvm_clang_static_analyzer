# Clang Static Analyzer 源码与部署说明

## 1. 定位

`Clang Static Analyzer` 是 Clang 内部的一套静态分析框架，核心能力是：

- 路径敏感分析
- 过程间分析
- 基于符号执行的缺陷发现

它不是一个独立仓库，而是 `llvm-project` 单仓中的一部分；源码主体位于：

- `clang/lib/StaticAnalyzer`
- `clang/include/clang/StaticAnalyzer`

---

## 2. 总体架构

从源码结构看，Static Analyzer 可以分成三层：

### 2.1 Frontend 层

负责把 Clang 前端的 `-analyze` 动作转换成具体分析任务，主要文件：

- `clang/lib/StaticAnalyzer/Frontend/FrontendActions.cpp`
- `clang/lib/StaticAnalyzer/Frontend/AnalysisConsumer.cpp`
- `clang/lib/StaticAnalyzer/Frontend/CheckerRegistry.cpp`
- `clang/lib/StaticAnalyzer/Frontend/CreateCheckerManager.cpp`

职责：

- 创建 `AnalysisConsumer`
- 解析 `AnalyzerOptions`
- 选择 `StoreManager` 和 `ConstraintManager`
- 创建 `CheckerManager`
- 驱动整个翻译单元的分析

### 2.2 Core 层

这是分析引擎本体，主要位于：

- `clang/lib/StaticAnalyzer/Core`
- `clang/include/clang/StaticAnalyzer/Core`

职责：

- 构建和维护抽象程序状态
- 驱动路径探索
- 建模符号值、内存区域、约束和存储
- 生成爆炸图 `ExplodedGraph`
- 组织缺陷报告

### 2.3 Checkers 层

主要位于：

- `clang/lib/StaticAnalyzer/Checkers`
- `clang/include/clang/StaticAnalyzer/Checkers`

职责：

- 通过回调挂到分析引擎的关键事件上
- 对特定缺陷模式建模
- 报告 bug，而不是自己实现路径搜索

---

## 3. 最重要的核心抽象

### 3.1 `ExprEngine`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/ExprEngine.h`
- `clang/lib/StaticAnalyzer/Core/ExprEngine.cpp`
- `clang/lib/StaticAnalyzer/Core/ExprEngineC.cpp`
- `clang/lib/StaticAnalyzer/Core/ExprEngineCXX.cpp`
- `clang/lib/StaticAnalyzer/Core/ExprEngineObjC.cpp`
- `clang/lib/StaticAnalyzer/Core/ExprEngineCallAndReturn.cpp`

它是表达式级别的解释器，也是整个 analyzer 最核心的对象。你可以把它理解成：

“在 CFG 上执行的抽象解释器 + checker 回调调度器”

主要工作：

- 模拟语句和表达式求值
- 在分支处拆分状态
- 管理函数调用和内联
- 调用 checkers
- 把新状态送入 `ExplodedGraph`

如果你只读一个核心类，优先读它。

### 3.2 `CoreEngine`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/CoreEngine.h`
- `clang/lib/StaticAnalyzer/Core/CoreEngine.cpp`

它负责通用的工作队列和 CFG 遍历机制。`ExprEngine` 建立在 `CoreEngine` 之上。

主要工作：

- 维护 worklist
- 从入口块开始推进分析
- 对每个 `ExplodedNode` 调度后续工作
- 控制最大步数、遍历策略和 CTU 相关队列

### 3.3 `ProgramState`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/ProgramState.h`
- `clang/lib/StaticAnalyzer/Core/ProgramState.cpp`

它表示“某个程序点上的抽象状态”，是整个 analyzer 的状态容器。

可粗略理解为三部分：

- `Environment`：表达式求值结果
- `Store`：内存绑定关系
- `GenericDataMap`：checker 自定义状态

同时它还关联约束信息，因此每条路径上都有自己的 `ProgramState`。

### 3.4 `ExplodedGraph`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/ExplodedGraph.h`
- `clang/lib/StaticAnalyzer/Core/ExplodedGraph.cpp`

图中的每个节点本质上是：

- `ProgramPoint`
- `ProgramState`

的组合。

它的作用是把一份普通 CFG “爆炸”成多条带状态的执行路径图，因此 analyzer 能区分：

- 同一语句在不同路径上的不同状态
- 某条路径可行、另一条路径不可行

### 3.5 `SVal`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/SVals.h`
- `clang/lib/StaticAnalyzer/Core/SVals.cpp`

`SVal` 是 analyzer 的值域抽象，表示：

- 未知值
- 未定义值
- 具体整数
- 符号值
- 位置值 `Loc`
- 非位置值 `NonLoc`
- 延迟聚合值

分析器不会直接拿 AST 节点做运算，而是大量围绕 `SVal` 传播值信息。

### 3.6 `MemRegion`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/MemRegion.h`
- `clang/lib/StaticAnalyzer/Core/MemRegion.cpp`

`MemRegion` 是内存对象抽象，用来表示：

- 栈变量
- 堆对象
- 全局对象
- 字段
- 数组元素
- 符号区域

这套抽象让 analyzer 能在“地址、对象、字段、偏移”层面跟踪内存。

### 3.7 `Store` / `RegionStore`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/Store.h`
- `clang/lib/StaticAnalyzer/Core/Store.cpp`
- `clang/lib/StaticAnalyzer/Core/RegionStore.cpp`

`Store` 是抽象接口，`RegionStore` 是默认实现。

职责：

- load / bind
- lvalue 建模
- 内存失效
- 聚合对象的惰性读取

默认使用的就是 field-sensitive 的 `RegionStore`。

### 3.8 `ConstraintManager`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/ConstraintManager.h`
- `clang/lib/StaticAnalyzer/Core/ConstraintManager.cpp`

职责：

- 对分支条件做 `assume`
- 判断约束是否可满足
- 收缩符号取值范围
- 删除失活符号

这是路径敏感分析成立的关键。

### 3.9 `RangeConstraintManager`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/RangedConstraintManager.h`
- `clang/lib/StaticAnalyzer/Core/RangeConstraintManager.cpp`

这是默认主力约束引擎，使用“范围集合”而不是重型外部求解器。

它适合处理：

- 整数范围
- 比较关系
- 分支约束收缩
- 一部分符号间关系

### 3.10 `SMTConstraintManager`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/PathSensitive/SMTConstraintManager.h`
- `clang/lib/StaticAnalyzer/Core/SMTConstraintManager.cpp`

这是可选的 SMT 约束后端。LLVM 的 CMake 文档说明：

- `LLVM_ENABLE_Z3_SOLVER=ON` 时启用
- 系统上必须有较新的 `z3` 库

因此：

- 默认部署并不强依赖 Z3
- 需要更强约束能力时可以把 Z3 编进来

### 3.11 `Checker` / `CheckerManager`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/Checker.h`
- `clang/include/clang/StaticAnalyzer/Core/CheckerManager.h`
- `clang/include/clang/StaticAnalyzer/Checkers/Checkers.td`

checker 通过事件回调工作，例如：

- `check::PreStmt`
- `check::PostStmt`
- `check::PreCall`
- `check::PostCall`
- `check::Location`

所以 checker 不负责路径搜索，而是在引擎推进时“观察并修正状态、发出告警”。

### 3.12 `BugReporter`

核心文件：

- `clang/include/clang/StaticAnalyzer/Core/BugReporter/BugReporter.h`
- `clang/lib/StaticAnalyzer/Core/BugReporterVisitors.cpp`

职责：

- 挂接 ExplodedGraph 生成报告路径
- 做路径裁剪、解释和输出格式化
- 输出 HTML、plist、SARIF 等结果

## 4. 主调用链

如果你想快速理解“从命令行到分析执行”发生了什么，可以按下面这条链读源码。

### 4.1 入口动作

`AnalysisAction::CreateASTConsumer()` 在：

- `clang/lib/StaticAnalyzer/Frontend/FrontendActions.cpp`

它会调用：

- `CreateAnalysisConsumer(CI)`

### 4.2 创建分析消费者

`CreateAnalysisConsumer()` 在：

- `clang/lib/StaticAnalyzer/Frontend/AnalysisConsumer.cpp`

它负责：

- 关闭 `-Werror` 的影响
- 读取 `AnalyzerOptions`
- 按需注入 model 文件
- 创建 `AnalysisConsumer`

### 4.3 处理翻译单元

`AnalysisConsumer::HandleTranslationUnit()` 是前端进入 analyzer 的主入口。

它会：

- 创建 `CheckerManager`
- 创建 `AnalysisManager`
- 根据选项跳过某些自动生成文件
- 调用 `runAnalysisOnTranslationUnit()`

### 4.4 遍历顶层声明

`runAnalysisOnTranslationUnit()` 会：

- 先运行 AST-only 检查
- 收集本 TU 顶层声明
- 在需要内联时按调用图顺序处理函数
- 最后运行 end-of-translation-unit checkers

### 4.5 处理单个函数

`AnalysisConsumer::HandleCode()` 会：

- 清理旧的分析上下文
- 取出 CFG
- 先跑语法级 checker
- 再在有 path-sensitive checkers 时调用 `RunPathSensitiveChecks()`

### 4.6 创建 `ExprEngine` 并执行

`AnalysisConsumer::RunPathSensitiveChecks()` 会：

- 检查 CFG 是否有效
- 检查活跃变量分析是否可用
- 构造 `ExprEngine Eng(...)`
- 调用 `Eng.ExecuteWorkList(...)`

### 4.7 执行工作队列

`ExprEngine` 底层依赖 `CoreEngine::ExecuteWorkList()`：

- 初始化入口 `ExplodedNode`
- 建立根节点
- 从 worklist 反复取出节点
- 分派到不同 program point 的处理逻辑
- 推进新状态
- 在结束时统一处理报告

可以把主流程简化成：

`FrontendAction -> AnalysisConsumer -> AnalysisManager -> ExprEngine -> CoreEngine -> ExplodedGraph + BugReporter`

## 6. 它能否离线部署

结论：**可以。**

Static Analyzer 本质上是 Clang 二进制的一部分，不依赖云端服务，也不要求联网才能运行。只要你把以下内容准备好，就可以完全离线部署：

- Clang/LLVM 源码包，或预编译安装包
- 构建工具链
- 可选依赖（例如 Z3）
- 目标项目自身的编译环境

### 6.1 最小离线部署方式

最简单的方法是：

1. 在可联网环境下载 `llvm-project` 源码或 release 源码包
2. 在离线环境准备好 `cmake`、编译器、构建工具
3. 只构建 `clang` 项目
4. 安装后直接使用 `clang --analyze` 或 `scan-build`

一个常见构建方式：

```bash
cmake -S llvm -B build -G Ninja \
  -DLLVM_ENABLE_PROJECTS="clang" \
  -DCMAKE_BUILD_TYPE=Release

cmake --build build
cmake --build build --target install
```

如果你不需要 SMT 支持，建议显式关掉 Z3 依赖，便于离线构建：

```bash
cmake -S llvm -B build -G Ninja \
  -DLLVM_ENABLE_PROJECTS="clang" \
  -DCMAKE_BUILD_TYPE=Release \
  -DLLVM_ENABLE_Z3_SOLVER=OFF
```

### 6.2 是否可以直接拷贝已编译产物

通常也可以，但有前提：

- 目标机和构建机的系统 ABI 兼容
- 依赖的运行库版本兼容
- 路径和动态库查找机制可满足

因此更稳妥的方式通常是：

- 在离线目标环境本机编译
- 或在相同系统版本的构建机编译后整体打包安装目录

### 6.3 如果要团队离线使用

有两种常见部署方式：

- 仅部署 `clang` / `scan-build`，面向个人和 CI
- 再额外部署 `CodeChecker`，用于团队化报告管理

其中：

- `scan-build` 是 LLVM 仓内工具，离线可用
- `CodeChecker` 是 out-of-tree 项目，不在 LLVM 仓内，需要单独准备离线安装包

## 7. 对操作系统和环境的要求

这里分成“运行 analyzer”和“从源码构建 analyzer”两类要求。

### 7.1 操作系统支持

仓库内 `CommandLineUsage.rst` 明确说明：

- `scan-build` 适用于主流平台：Windows、Linux、macOS

构建系统文档也明确支持以下主流生成器：

- `Ninja`
- `Unix Makefiles`
- `Visual Studio`
- `Xcode`

因此实际可部署主机主要就是：

- Linux
- macOS
- Windows

### 7.2 构建工具要求

LLVM 官方 CMake 文档说明：

- 最低 `CMake` 版本：`3.20.0`

LLVM 顶层 `CMakeLists.txt` 说明：

- 构建 LLVM 需要 `C++17`

常见推荐工具：

- `Ninja`
- 或 `Unix Makefiles`
- Windows 下用 `Visual Studio`
- macOS 下也可用 `Xcode`

### 7.3 主机 C++ 工具链要求

`llvm/docs/GettingStarted.rst` 给出的常见最低 host toolchain 版本是：

- `Clang 5.0`
- `Apple Clang 10.0`
- `GCC 7.4`
- `Visual Studio 2019 16.8`

文档同时说明：

- 更老版本“可能能编”，但不属于受支持主机平台
- 在 macOS 上通常需要足够新的 Xcode
- Windows 上推荐 Visual Studio 2019 或更高版本

### 7.4 Windows 特殊要求

`GettingStartedVS.rst` 给出的信息包括：

- Visual Studio 2019 或更高
- CMake
- Python 3.8+
- Git for Windows

另外，Analyzer 文档指出：

- Windows 上用 `scan-build` 需要安装 `Perl`

所以如果你在 Windows 上想完整使用 analyzer 命令行工具，比较稳妥的最小集是：

- Visual Studio 2019/2022
- CMake
- Perl
- Git

如果要跑测试，再加：

- Python 3.8+

### 7.5 Z3 是否必需

不是。

LLVM 的 CMake 文档说明：

- `LLVM_ENABLE_Z3_SOLVER` 是可选项
- 开启时系统上必须有较新的 `z3` 库

所以：

- 默认离线部署可以不带 Z3
- 需要 `SMTConstraintManager` 或相关增强能力时，再单独准备 Z3

### 7.6 Python、Perl、CodeChecker 是否必需

取决于你怎么用 analyzer。

#### 只想运行 `clang --analyze`

通常不需要：

- Python
- Perl
- CodeChecker

#### 想用 `scan-build`

- Linux/macOS：通常直接可用
- Windows：需要 `Perl`

#### 想用 `CodeChecker`

需要单独部署 `CodeChecker`，它不是 LLVM 单仓的一部分。

### 7.7 CTU 支持的现实边界

仓库文档明确说明：

- `scan-build` 不支持 CTU
- `CodeChecker` 在 Linux 上完整支持 CTU

所以如果你的目标是：

- 离线
- 扫复杂 C++ 项目
- 需要跨翻译单元

更现实的组合通常是：

- Linux
- `compile_commands.json`
- `CodeChecker`
- 可选的 Z3

## 8. 面向离线场景的建议

### 8.1 如果只是个人研究源码

建议：

- 本机构建 `clang`
- 不启用 Z3
- 直接使用 `clang --analyze`

### 8.2 如果是企业内网离线部署

建议：

- 优先 Linux 服务器或 Linux CI 节点
- 固定一套 `clang + scan-build` 或 `clang + CodeChecker`
- 提前准备源码镜像、依赖镜像和构建工具链
- 用 `compile_commands.json` 驱动复杂项目

### 8.3 如果只关心扫描而不关心二次开发

建议直接部署安装产物而不是完整源码树；源码主要保留给：

- 调试 analyzer
- 二次开发 checker
- 理解误报来源

---

## 9. 一句话结论

`Clang Static Analyzer` 的源码结构非常清晰：前端负责接入，`ExprEngine` 和 `CoreEngine` 负责路径执行，`ProgramState`/`SVal`/`MemRegion`/`Store`/`ConstraintManager` 构成抽象语义层，checkers 负责具体缺陷规则。

从部署角度看，它完全可以离线使用；最小要求是准备好一套能构建 Clang 的现代 C++17 工具链和 `CMake 3.20+`。若只做基础部署，不需要 Z3；若要用 `scan-build`，Windows 还需要 Perl；若要在复杂项目上稳定做 CTU，优先考虑 Linux + CodeChecker。
