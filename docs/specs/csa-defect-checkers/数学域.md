# 增强需求：数学函数域保护检查 (MathDomainGuard)

**Workspace**: `csa-defect-checkers`
**Created**: 2026-03-17
**Status**: Draft
**基线**: MVP 已完成 `alpha.security.MathDomain` CSA Checker（仅检测编译期常量违反）

---

## 1. 问题描述

当前 `alpha.security.MathDomain` CSA Checker 只能检测**编译期常量**的域违反（如 `sqrt(-1.0)`），无法处理变量参数。原因是 CSA 的符号执行引擎不支持浮点符号化（`SymbolManager::canSymbolicate()` 对 `float`/`double` 返回 `false`），导致以下两类场景均无法检出：

### 场景 A: 路径约束为负

```cpp
void f(double x) {
    if (x < 0) {
        double y = sqrt(x);  // 当前不报 — CSA 无浮点符号值，无法利用 x < 0 约束
    }
}
```

### 场景 B: 完全未约束

```cpp
void g(double x) {
    double y = sqrt(x);      // 当前不报 — 无法判断 x 正负，保守策略下不报
}
```

### 根因分析

| 技术路线 | 场景 A | 场景 B | 可行性 |
|---------|--------|--------|--------|
| 扩展 CSA 符号引擎支持浮点 | ✅ | ❌（仍只报必定） | 极高复杂度，不现实 |
| 新 CSA Checker "可能违反"策略 | ❌（无浮点符号值） | ❌ | 引擎限制无法绕过 |
| **clang-tidy AST 检查** | **✅** | **✅** | **低复杂度，推荐** |

---

## 2. 推荐方案：新建 `bugprone-math-domain-guard` clang-tidy Check

### 设计思路

**放弃路径分析，转而检查调用点的 AST 上下文**：每个 `sqrt`/`asin`/`acos` 调用，检查其参数是否有"域保护"（guard）。

域保护的定义：在调用点之前的控制流中，存在对参数的域合法性判断。

### 架构定位

两个检查器形成互补层次：

| 层级 | 工具 | 检测内容 | 检测方式 |
|------|------|---------|---------|
| 常量域违反 | `alpha.security.MathDomain` (CSA) | `sqrt(-1.0)`, `asin(2.0)` | 编译期常量求值 |
| 变量域未验证 | `bugprone-math-domain-guard` (clang-tidy) | `sqrt(x)` 无保护, `if(x<0) sqrt(x)` | AST 模式匹配 |

### 技术方案

**所属模块**: `clang-tools-extra/clang-tidy/bugprone/`
**注册名称**: `bugprone-math-domain-guard`
**继承**: `ClangTidyCheck`

**核心流程**:

```
registerMatchers(MatchFinder *Finder):
  Finder->addMatcher(
    callExpr(
      callee(functionDecl(hasAnyName(
        "sqrt", "sqrtf", "sqrtl",
        "asin", "asinf", "asinl",
        "acos", "acosf", "acosl"
      ))),
      hasArgument(0, expr().bind("arg"))
    ).bind("call"),
    this
  );

check(MatchResult &Result):
  1. 获取 callExpr 和 arg
  2. 跳过编译期常量参数（交给 MathDomainChecker 处理）
  3. 获取参数引用的变量（DeclRefExpr）
  4. 确定函数类型和对应的域要求:
     - sqrt 系列: arg >= 0
     - asin/acos 系列: -1 <= arg <= 1
  5. 向上查找 call 所在的 IfStmt:

     情况 A — call 在 if 的 then 分支中:
       分析 if 条件:
       ┌─────────────────────────┬─────────────────────┐
       │ if 条件                  │ 判定                │
       ├─────────────────────────┼─────────────────────┤
       │ arg >= 0 / arg > 0      │ 正向保护 → 不报     │
       │ arg < 0 / arg <= -1     │ 反向保护 → 报！     │
       │ arg >= -1 && arg <= 1   │ 正向保护 → 不报     │
       │ 与参数无关的条件         │ 视为无保护 → 报     │
       └─────────────────────────┴─────────────────────┘

     情况 B — call 在 if 的 else 分支中:
       条件取反后同上分析

     情况 C — call 不在任何 if 中:
       无域保护 → 报"参数未经域验证"

  6. 特殊模式识别:
     - assert(x >= 0); sqrt(x);  → 已保护，不报
     - x >= 0 ? sqrt(x) : 0.0;  → 已保护，不报
     - fabs(x) → sqrt 对 fabs 结果调用时，不报（fabs 结果恒非负）
```

### 诊断消息

| 场景 | 消息 |
|------|------|
| 反向保护 | `"calling sqrt(x) in a branch where x < 0 is guaranteed"` |
| 无保护 | `"argument to sqrt is not validated; ensure it is non-negative before calling"` |
| asin/acos 无保护 | `"argument to asin is not validated; ensure it is in [-1, 1] before calling"` |

### 保护模式识别细节

**if 守卫（核心模式）**:

```cpp
// 正向保护 — 不报
if (x >= 0) {
    sqrt(x);       // ✅ 保护条件直接约束参数为非负
}

// 反向保护 — 报！
if (x < 0) {
    sqrt(x);       // ⚠️ 保护条件约束参数为负，在负值分支中调用
}

// else 分支正向保护 — 不报
if (x < 0) {
    handle_error();
} else {
    sqrt(x);       // ✅ else 分支中 x >= 0
}
```

**assert 模式**:

```cpp
assert(x >= 0);
sqrt(x);           // ✅ assert 相当于前置保护
```

**三目运算符**:

```cpp
double y = (x >= 0) ? sqrt(x) : 0.0;  // ✅ 条件表达式中已保护
```

**fabs 模式**:

```cpp
sqrt(fabs(x));     // ✅ fabs 结果恒非负，不报
```

### 条件匹配实现

AST 层面分析 `IfStmt` 的条件表达式：

```
matchGuardCondition(IfStmt *If, VarDecl *ArgVar, FunctionType funcType):
  Cond = If->getCond()

  如果 Cond 是 BinaryOperator:
    如果是 >=, >, ==, <=, < 中的一种:
      检查 LHS 或 RHS 是否引用 ArgVar
      检查另一侧是否是数字常量
      根据运算符和常量值判断是否为"域保护":

        对于 sqrt:
          x >= 0  →  保护 ✅
          x > 0   →  保护 ✅
          x < 0   →  反向 ⚠️
          x <= 0  →  反向 ⚠️  (包含 x == 0 但 sqrt(0) 合法，仍算反向)

        对于 asin/acos:
          x >= -1 && x <= 1  →  保护 ✅  (需检查 &&)
          仅 x >= -1         →  部分保护，仍报

  如果 Cond 是 UnaryOperator(!) 且内部是上述 BinaryOperator:
    取反后分析
```

### 可配置选项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `WarnOnUnguardedCall` | bool | true | 是否对无保护的调用报警 |
| `RecognizeAssertAsGuard` | bool | true | 是否将 assert 视为保护 |
| `RecognizeFabsAsGuard` | bool | true | 是否将 fabs 结果视为安全 |

## 3. 验收场景

### 场景 1: 反向保护 — 在负值分支中调用 sqrt（应报警）

```cpp
void f(double x) {
    if (x < 0) {
        double y = sqrt(x);  // WARN: "calling sqrt(x) in a branch where x < 0"
    }
}
```

### 场景 2: 完全无保护的 sqrt 调用（应报警）

```cpp
void g(double x) {
    double y = sqrt(x);      // WARN: "argument to sqrt is not validated"
}
```

### 场景 3: 正向保护 — 已验证非负（不应报警）

```cpp
void h(double x) {
    if (x >= 0) {
        double y = sqrt(x);  // OK
    }
}
```

### 场景 4: else 分支中的正向保护（不应报警）

```cpp
void k(double x) {
    if (x < 0) {
        return;
    }
    double y = sqrt(x);      // OK — x < 0 已被 early return 排除
}
```

> 注：此场景需要分析 if 的 early return 模式。初始实现可暂不覆盖此模式，标记为 Known Limitation。

### 场景 5: fabs 保护（不应报警）

```cpp
void m(double x) {
    double y = sqrt(fabs(x)); // OK — fabs 结果恒非负
}
```

### 场景 6: 编译期常量（不应报警 — 交给 MathDomainChecker）

```cpp
double y = sqrt(-1.0);       // 本 Check 跳过，由 MathDomainChecker 报
```

### 场景 7: asin 无保护（应报警）

```cpp
void p(double x) {
    double y = asin(x);      // WARN: "argument to asin is not validated"
}
```

### 场景 8: acos 已保护（不应报警）

```cpp
void q(double x) {
    if (x >= -1.0 && x <= 1.0) {
        double y = acos(x);  // OK
    }
}
```

## 4. 边界情况

- `sqrt(0.0)` 是合法调用，正向保护条件 `x >= 0` 包含 0
- `asin(1.0)` 和 `acos(-1.0)` 是边界合法值
- 参数为复杂表达式（如 `sqrt(a + b)`）：初始实现仅处理简单变量引用，复杂表达式标记为"无保护"报警
- C++ `std::sqrt` vs C `sqrt`：两者都需匹配
- 宏内调用：`isExpansionInMainFile()` 过滤宏展开内的调用（可配置）
- 模板函数中的调用：按模板实例化后的 AST 分析

## 5. 误报控制

| 误报来源 | 示例 | 控制措施 |
|---------|------|---------|
| 参数由保证非负的外部函数返回 | `sqrt(compute_positive_value())` | 无法自动消除；用户可通过 `// NOLINT` 抑制 |
| early return 保护模式未识别 | `if (x < 0) return; sqrt(x);` | 初始版本可能误报，后续增强 |
| 物理量恒正（如长度、面积） | `sqrt(length)` | 需用户保证变量语义；工具无法推导 |

**总体误报预期**: 中等。对于无保护的 `sqrt(x)` 调用，确实应该有域检查，报警是合理的。主要误报来源是"已在别处保证合法但本 Check 未识别到保护模式"的情况。

### 降低误报的渐进策略

1. **V1 (初始)**: 仅识别直接 `if` 包裹的保护模式
2. **V2 (增强)**: 增加 early return 模式（`if (x < 0) return;`）
3. **V3 (高级)**: 增加 assert、三目运算符、`fabs` 模式

### Phase 2: 增强保护模式

- fabs 保护识别
- 复杂表达式参数处理
- 嵌套 if 中的保护传播

## 7. 备选方案（参考）

### 备选 A: 扩展 CSA 符号引擎

修改 `SymbolManager`、`ConstraintManager`、`SValBuilder` 使其支持浮点符号化。

- 优点：从根本上解决问题，路径分析完全精确
- 缺点：工作量极大（几周到几个月），影响 CSA 核心引擎稳定性
- 状态：不在可行范围内

### 备选 B: 混合方案

整数参数用 CSA 路径敏感分析，浮点参数用 clang-tidy AST 检查。

- 评估：本方案实质上就是 B 的浮点部分。整数部分已由 `alpha.security.MathDomain` 的 `SVal` 逻辑覆盖（虽然实际场景中数学函数参数几乎都是浮点）。
